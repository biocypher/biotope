## Purpose and outcome

Integrate the updated croissant-baker so Vlad can work with Daria and INTRAC data manually or through an agent. The supported workflow ends with mappings:

1. Scan local raw data through baker to create a description of its structure.
1. Define a purpose and target schema using the existing project and mapping artifacts.
1. Author mappings between described source fields and the target schema.
1. Validate metadata and mapping definitions without executing them against source values.

Baker owns source-format parsing. Biotope manages the resulting metadata and mappings. Project-specific data loading and transformation belong to later work in each project. This iteration must not introduce another reader layer or redesign the mapping engine.

The practical outcome is correct metadata, understandable CLI output, usable mapping tools and a simple runbook that Vlad can follow. Compatibility with earlier artifacts or removed commands is not required; regeneration is acceptable.

## Scope

### Integrate and retain

- Use the local merged baker checkout during development. Before release, require a published baker version containing the tested changes.
- Preserve baker's descriptions through both directory and single-file ingestion, including record-set identities, sheets, nested fields, source references and compression metadata.
- Keep metadata inspection, purpose capture, mapping scaffolding/editing, the mapping wizard and metadata-based validation usable from the CLI and their supporting APIs.
- Keep the current target-schema representation as it is. Purpose and entity/relation lists remain in project metadata; detailed schema choices remain in mappings.
- Retain existing workspace setup, configuration, annotations, provenance, workflow status, file tracking and Git utilities. Preserve metadata-based alignment suggestions where they already work.
- Audit the complete Biotope test suite and aggressively prune bloat while preserving protection for retained behavior. Retire tests for the downstream functionality left unsupported in this iteration.
- Make only the documentation and skill changes needed to describe the resulting workflow accurately.

### Remove

- Biotope's custom raw-data readers, including reader implementations embedded in or copied by templates. Remove source sampling, sample rows, sample mapped tuples and execution-based previews from CLI, wizard and API paths.
- Validation that depends on those readers or on executing mappings against source values. Do not replace it with another loader or a new baker reader API. Keep existing checks that operate on metadata and mapping definitions: structure, declared record sets and fields, selectors, relation references, unresolved bindings and definition conflicts.
- `annotate load`, which currently delegates record loading to `mlcroissant` and is outside the metadata workflow.
- Downloading and discovery: `get`, `search` and `discover`, their public entry points and feature-specific implementations, registry clients, configuration defaults and examples. Remove dependencies used exclusively by these features; preserve shared utilities needed by retained functionality.
- Text knowledge extraction: `read` and its placeholder implementation, entry points and examples.

Remove obsolete tests and active documentation for deleted behavior. Removed commands and sample flags must not remain as silent no-ops or compatibility shims. Reading manifests, mappings, configuration and file-tracking information remains valid. Existing checksum checks may read bytes; they must not become data-value inspection. Baking itself necessarily reads raw data through baker.

### Out of scope

Graph construction, mapping execution, loaders and transformations, generated graph adapters, graph export, querying, graph inspection and benchmarking may remain dangling or broken. The explicit reader removals above take precedence, including readers used by graph code or templates. Leave the rest alone. Detach imports, calls or command registration where needed to keep the supported workflow and test collection operational; no downstream replacement or compatibility layer is required.

Delete tests that protect only these downstream features. Extract useful checks for retained behavior from mixed tests before removing their downstream portions. Keep tests proving that dangling code cannot break the supported commands.

Also excluded: a new target-schema design, Paul's typed Python backbone, richer purpose elicitation, paper experiments, new format support including Zarr, a reusable baker reader API, preprocessing, scientific analysis, automated agent evaluation infrastructure, migration tooling and broad architecture cleanup. Removal of downloading/discovery is in scope; building replacements is not.

## Required behavior

### Metadata fidelity

Directory and single-file ingestion must use baker's assembly contracts without flattening richer descriptions into a single table. Distinct record sets must remain selectable even when their display names collide, such as identically named sheets in different workbooks. Existing supported formats must remain usable alongside the new handlers.

Do not manufacture fields or imply support where baker has only recorded a file or described part of it. Fix small integration defects found during this work; record format limitations that require separate baker work.

### Diagnostics

During ingestion, show meaningful progress. Final output must distinguish successful structural descriptions, partial descriptions, unsupported inputs and parsing failures, with identifiable files and reasons where available. A registered file or populated field list does not establish that a mapping can execute or that data is ready for a graph.

Account for the selected inputs so a user can reconcile the messages with the manifest and identify files with no structural description. Use baker's available evidence; if coverage is unknown, say so. Do not add independent payload exploration or invent a completeness score. Keep existing human-readable and structured outputs consistent without creating a new reporting API.

### Mapping and validation

Inspection, scaffolding, the wizard and structural validation must work from existing metadata even when the source payloads are unavailable. Remove value samples from both human-readable and structured output. A structural summary of the proposed mapping remains useful.

Report incomplete or invalid mappings clearly, with the affected field or binding. A passing result means the retained structural checks passed; it must not imply valid source values, successful transformations or graph correctness. Existing metadata validation may remain where it does not load source records. The implementer may choose a clearer command name for the remaining mapping checks.

## Test-driven development

For each change to product behavior, including removal of a public feature, use this order:

1. Define the intended behavior in a focused automated test tied to an acceptance criterion. Reuse an adequate existing regression test when available.
1. Run it against the current implementation and observe failure for the intended reason. Fix an invalid test before proceeding.
1. Implement the smallest change that satisfies the test.
1. Run the test and relevant regression checks. Refactor only with those checks passing.
1. Record the test, the observed failure and the passing result in the log, grouped by change where useful.

Do not implement first and add confirming tests afterward. Public feature removals can share a compact CLI/API contract test; internal helper deletions do not need individual absence tests. Establish continued operation of retained paths, then delete the feature and retire its obsolete tests. Unchanged behavior may already pass its baseline tests; do not introduce artificial failures for the TDD log. Metadata-only tests should exercise actual commands or APIs with unavailable source payloads.

Use small deterministic fixtures and real baker calls for integration contracts; mocked responses alone are insufficient. Cover distinct metadata shapes and integration risks across existing tables, compression, new format families, multiple record sets, unsupported and malformed input. Do not repeat every format through every command or reproduce baker's handler test suite. Fixture expectations must be known independently of baker's output. Keep production datasets out of the automated suite.

Use existing tools and conventions. Run focused tests during development and the retained suite and applicable checks at handoff. Broaden or repeat checks only for new changes, failures or unresolved risks. Docs and skill edits need consistency review, not a new test framework.

## Test debloating

Review the complete Biotope suite, including assertions, fixtures, mocks, parameter sets, skips and expected failures. Inventory the collected tests and account for files that cannot collect. Do not limit the audit to tests touched by the integration changes. Record findings and decisions in `01-croissant-baker-update.test-audit.md` beside this spec; implementation includes pruning, not just recommendations.

Identify and list:

- **Phantom tests:** assertions that always pass or always fail regardless of product behavior, unreachable assertions, swallowed failures and tests that only confirm their own mock setup. A test exposing a real defect is not phantom because it fails.
- **Trivial tests:** checks of constants, plain accessors, framework behavior or implementation details that protect no meaningful Biotope contract.
- **Redundant tests:** duplicate scenarios, repeated assertions across layers and parameter variations that exercise no distinct behavior or failure mode.
- **Overly granular tests:** fragments of one behavior that a concise integrated test could protect more clearly and economically. Consolidate where this preserves useful failure diagnosis; focused unit tests are not bloat merely because they are small.
- **Obsolete tests:** tests for removed features, old compatibility promises and the downstream graph functionality left unsupported here.
- **Other bloat:** stale skips or expected failures, oversized snapshots, unnecessary fixture/setup machinery, excessive mocking and repeated expensive setup without additional protection. Treat these as candidates for review, not automatic grounds for deletion.

List each finding by test ID or an explicit file/group and include its category, decision (`delete`, `merge`, `rewrite` or `keep`), reason and the exact retained or replacement tests protecting any still-supported behavior. For unsupported behavior, record that retirement is intentional. Summarize which files were reviewed; group equivalent findings to keep the report readable.

Prune decisively. Remove orphaned fixtures, helpers, snapshots, test-only dependencies and collection configuration when no retained tests need them. Do not leave obsolete tests permanently skipped or expected to fail. Avoid replacing many small tests with one large test that hides unrelated failures.

Preserve distinct boundaries, error paths, known-regression cases and real baker integration coverage. Shared code coverage or similar test names do not establish redundancy. Before deleting useful assertions, identify where their behavior is still checked; write and verify replacement tests first when needed. Do not weaken assertions, broaden tolerances or remove a real failing regression to make the suite pass.

Where assertion review is insufficient, check whether a suspect test detects a relevant faulty input or temporary, reversible product fault. A phantom test may keep passing; record that lack of sensitivity as the finding. Verify that its replacement, if needed, detects the intended fault, restore the correct state and rerun. Keep this targeted; no mutation-testing framework or meta-tests about test deletion are required.

Record before/after collected counts, including parameterized cases, commands and results. The retained suite must collect; automated checks for implementation readiness and new or changed tests must pass. Regressions introduced by this work block completion. An unrelated pre-existing failure may be deferred only with reproducible baseline evidence and a recorded reason; keep its useful regression test and report the suite honestly. A failure affecting an acceptance criterion blocks that criterion. Do not turn this audit into unrelated product repairs or delete valid failures to obtain a green report. Counts, runtime and coverage percentages alone do not prove protection; there is no deletion quota.
