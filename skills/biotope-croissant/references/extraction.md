# Extracting records from documents

Documents, such as papers, saved web pages and calls, go through extraction: an extractor reads each document under an extraction schema and returns records whose values carry their evidence. `biotope extract run` stores them and registers them as a processed dataset, which you then generate and map like a table. The contracts are in the Biotope documentation page "Extraction".

## Who decides what

- The user decides which documents may go to an external model. Send only public documents, such as published papers, public web pages and public calls. When a document is internal, confidential or of unknown status, do not extract it with a model: ask the user, and transcribe its facts by hand as a document source if they agree.
- The user decides what the schema extracts: which kinds of document, which fields, what each field means and which fields identify a record. You propose; the user approves. A field description is a scientific definition, like a topology description.
- You decide the engineering: field types, the record key's mechanics, the module layout and the commands. The model and endpoint are the project's choice; ask when the configuration does not name them, and never choose a default.

## Steps

1. Register the documents with `biotope add <data-path> --json`, as in Step 3.
1. Read the purpose and its competence questions or user stories, then a few sample documents of each kind. Derive the schema from the questions, not from the documents' layout:
   - Write each question or user story as the query a user would run, such as "which PIs work on topic X", "which calls accept PhDs from year Y" or "which studies compare day 3 with day 0 in mouse". Name the field each query filters, searches or sorts on, and its value type. A query needs a field with short, comparable values, such as a list of topics, methods or scales, or a number or `Literal` for a range or category; a prose field can be read but not filtered. Propose these fields yourself, without waiting for the user to ask, and say which query each serves.
   - List the values each answer needs to be read correctly, such as the direction of a change, the reference group, and whether the groups are the same individuals, and propose one field per value.
   - A field no question needs is left out; a question no field serves is named as a gap.
   - Decide which records the purpose needs. A record stands for something the purpose asks about and the document itself reports, such as a comparison whose result the paper states. Say in the docstring which records to extract and which to leave out, such as validation assays or contrasts the questions do not ask about. Never ask for records the document does not report, and never construct one from parts of the document.
1. Write one schema per kind of document as a dataclass in `graph/extraction/<kind>.py`, after `biotope graph scaffold`, declared `@dataclass(frozen=True, kw_only=True)`: a docstring saying what the document is and which records to extract, and a `description` for every field that says exactly what to fill and what not to (for example "organisms whose samples the study analysed", not "organisms"). Declare `__record_key__` when a document holds several records, such as the rounds of a call or the comparisons of a study. `biotope extract schema graph/extraction/<kind>.py:<Class>` prints the fields, the key and the revision as biotope reads them; use it instead of importing biotope. `graph check` type-checks these modules with the rest of the graph code.
1. Check that `.biotope/config.yaml` has an `extraction` section with the extractor, endpoint, model and `key_env`. The key stays in the environment variable; never write it into a file, a command line or a message.
1. Run `biotope extract try graph/extraction/<kind>.py:<Class> <sample>... --json` on two or three representative documents, including the one with the most records. It prints one progress line per document to stderr. Run it in the foreground with a long timeout and wait for it to finish; do not poll with `sleep`.
1. Check the `try` output yourself before showing it:
   - For a sample of values, and for every value in `unaligned` and `weak`, read the quote and its context in `biotope extract text <file>` (the evidence's `start` and `end` are offsets into that text) and ask whether the value answers the field's description. A `weak` quote is short, shorter than 30 characters and found more than once, or found only in a PDF's running heads or footers: it was found, but it does not show that the value is right, so judge it from the context.
   - Compare the records with the document: list the records that should not exist and the ones that are missing.
   - Treat an `empty` document as a miss until the document shows it states nothing.
   - Treat an `unsupported` document as wrong: most values of a record listed under `unsupported` are not in the document or quote only its running heads, so the model probably answered from memory or from page furniture.
   - Where values or records are wrong, sharpen the docstring and the field descriptions and run `try` again.
1. Show the user each field with the query or question it serves, and the `try` output: each value, its quote, whether the quote was found, the weak evidence, the records you judged wrong or missing, and what you checked and changed. Revise the schema with the user until they approve it.
1. Any change to the schema after the user approved it, however small, makes a new revision: run `try` again on the same samples, check the output as above, and get the user's approval of the changed schema before `run`. Do this also when the user said they do not need to see the output: tell them what changed in the records.
1. After the user approves the schema as it stands, run `biotope extract run graph/extraction/<kind>.py:<Class> <dataset>... --json`, in the foreground as for `try`. It keeps each document as it finishes and writes the output when the run completes; when a run is interrupted, run it again: it reuses the finished documents and reports every change since the last completed run. When the report has a warning that the schema revision was never shown with `try`, stop: the stored records come from a schema the user has not seen tried. Run `try` on the samples, check it, get the user's approval as in the step above, and run again. Read the report: fix or report every `failed` and `missing` document, check every `empty` document, check each `unaligned` and `weak` value against the document text, and explain disappeared and appeared record IDs. The records go to `data/extracted/<kind>.jsonl`. Report `ignored` files to the user: they must be committed, so `.gitignore` needs an exception.
1. Check the stored records of every document as in the `try` check. Re-extract every document whose records you judge wrong, including `empty` and `unsupported` ones, with one run that names each of them: `--redo <file>` once per document. Check the new records the same way. A model's values vary between runs, so re-extract only documents whose records are wrong. When a document is still wrong, the schema or its descriptions need work: go back to the user. A document still `unsupported` after `--redo` is either redone with a sharper schema or dropped from its dataset with the user's agreement; never hand it over as extracted. Tell the user about every `unsupported` document and what you did with it. In the hand-over, list each document you re-extracted, why, and whether it is now right.
1. Run `biotope source generate .biotope/datasets/data/extracted/<kind>.jsonl.jsonld --out graph/sources` and continue with Step 4. Each record's `id` is the identity to keep; a loader yields one record per line and cites the document, the record's `document_sha256` as the version, and the value's page and quote as the location.

Never edit the extracted records or their manifest by hand: a later run rewrites them. Correct a wrong value through the schema and a new run, or exclude the record in a mapping against a declared policy. Field descriptions come from the schema; dataset fields, such as a description or a URL, go into the records file's annotation file, for example `biotope annotate set data/extracted/<kind>.jsonl description="..."`. Move a records file only with `biotope mv`, which moves its extraction state, then pass the new path to `--out`.

Run `biotope extract run` again after documents change; unchanged documents are reused without a model call, and the report says what changed.
