# Extracting records from documents

Documents, such as papers, saved web pages and contracts, go through extraction. You write one extractor per kind of document in the project's graph workspace, and Biotope runs it: it hands each matched document to the extractor, validates the records, reuses unchanged ones, stores them and registers them as a processed dataset, which you then generate and map like a table. The contracts are in the Biotope documentation page "Extraction".

## Who decides what

- The user decides which services may process the documents and how keys are supplied. Ask before any document goes to an external service. Keys stay in environment variables the extractor reads; never write one into a file, a command line or a message.
- The user decides what the schema extracts: which kinds of document, which fields, what each field means and which fields identify a record. You propose; the user approves. A field description is a scientific definition, like a topology description.
- You decide the engineering: how each kind of document is read, the extractor's code, field types and the record key's mechanics. You may discuss organising the data folder with the user, so that each kind of document is easy to route.

## Approach

- Sort the documents by how they are built before you run `biotope add` and before writing any extractor: which files are structured data and which are documents, and which documents share a structure, such as papers, a website's profile pages or contracts. A suffix or folder alone does not tell: a folder of papers can hold PDFs and text files of one kind, and tab-separated `.txt` files are tables. One kind of document gets one extractor.
- Read structure with code and give a model only what needs language. Headings, tables, page numbers and the elements of a page are read with an established library; a model gets only the passages a value must be read from.
- Fail loudly: when a document lacks the structure the extractor expects, raise `ExtractionError` with the reason, rather than return partial or empty records.
- Keep evidence with each value: the quote the value comes from, or a locator such as a page and section, so a reader can check it and a loader can cite it.

## Steps

1. Register the documents with `biotope add <data-path> --json`, as in Step 3.
1. Read the purpose and the questions agreed in Step 2, then a few sample documents of each kind. Derive the schema from the questions, not from the documents' layout:
   - Write each question as the query a user would run, such as "which PIs work on topic X", "which calls accept PhDs from year Y" or "which studies compare day 3 with day 0 in mouse". Name the field each query filters, searches or sorts on, and its value type. A query needs a field with short, comparable values, such as a list of topics, methods or scales, or a number or `Literal` for a range or category; a prose field can be read but not filtered. Propose these fields yourself, without waiting for the user to ask, and say which query each serves.
   - List the values each answer needs to be read correctly, such as the direction of a change, the reference group, and whether the groups are the same individuals, and propose one field per value.
   - A field no question needs is left out; a question no field serves is named as a gap.
   - Decide which records the purpose needs. A record stands for something the purpose asks about and the document itself reports. Say in the docstring which records to extract and which to leave out. Never ask for records the document does not report, and never construct one from parts of the document.
1. Copy `graph/extraction/template.py` to `graph/extraction/<kind>.py` for each kind of document and delete its first line, `# biotope:placeholder`. Write the schema: a dataclass declared `@dataclass(frozen=True, kw_only=True)` with a docstring saying what the document is and which records to extract, a `description` for every field that says exactly what to fill, and `__record_key__` when a document holds several records. Write the extractor: a subclass of `biotope.extraction.Extractor` with `name`, `version` and `settings`, the values that shape its output such as the model, and an `extract` that reads `document.path`. Shared reading code goes in a module of its own in `graph/extraction/`, imported with a relative import.
1. List each extraction in `graph/extraction/__init__.py` with its name, schema, extractor, the file patterns it reads, relative to the project root, and `parallel`, how many documents it takes at once. A pattern routes documents by folder or name, such as `data/pages/*.html` or `data/inbox/contract_*.pdf`. Biotope runs `extract` in threads when `parallel` is above 1: guard a library that is not thread-safe, such as `pypdfium2`, with a lock, or keep `parallel` at 1. Run `biotope graph check`; it type-checks the extraction code.
1. Run `biotope extract try <name> <sample>... --json` on two or three representative documents, including the one with the most records, in the foreground with a long timeout.
1. Check the `try` output yourself before showing it: compare each record with its document, check a sample of values against their quotes or locators, list the records that should not exist and the ones that are missing, and treat an `empty` document as a miss until the document shows it states nothing. Where values or records are wrong, fix the extractor or sharpen the descriptions and run `try` again.
1. Show the user each field with the question it serves, and the `try` output: each value with its evidence, the records you judged wrong or missing, and what you checked and changed. Revise the schema with the user until they approve it.
1. Any change to the schema after the user approved it makes a new revision: run `try` again on the same samples, check it, and get the user's approval before `run`. Whenever the extractor's behaviour changes, raise its `version`, so the next run extracts every document again.
1. After the user approves, run `biotope extract run --json`, in the foreground as for `try`; it runs every listed extraction, or the ones you name. When a run is interrupted, run it again: it reuses the documents it finished. Read the report: fix or report every `failed` document, check every `empty` one, and explain disappeared and appeared record IDs. Report `ignored` files to the user: they must be committed, so `.gitignore` needs an exception.
1. Check the stored records of every document as in the `try` check. Re-extract each document whose records you judge wrong with `--redo <file>`, and check it again. When a document is still wrong, the schema or the extractor needs work. In the hand-over, list each document you re-extracted, why, and whether it is now right.
1. Run `biotope source generate .biotope/datasets/data/extracted/<name>.jsonl.jsonld --out graph/sources` and continue with Step 4. Each record's `id` is the identity to keep; a loader yields one record per line and cites the document, the record's `document_sha256` as the version, and the value's quote or locator as the location. `source generate` writes no package for a document an extraction has read.

Never edit the extracted records or their manifest by hand: a later run rewrites them. Correct a wrong value through the extractor or the schema and a new run, or exclude the record in a mapping against a declared policy. Dataset fields, such as a description or a URL, go into the records file's annotation file, for example `biotope annotate set data/extracted/<name>.jsonl description="..."`. The records file is always `data/extracted/<name>.jsonl`; to change it, rename the extraction, run it and remove the old file with `biotope rm`. To drop an extraction, delete it from the list and remove its records file the same way; `biotope rm` also removes its run state, so its documents get packages again.

Run `biotope extract run` again after documents change. The records mirror the files the patterns match now: a new file joins, a removed one loses its records, and a moved file keeps them only while a pattern still matches it, under IDs from its new path unless its whole dataset folder moved. Unchanged documents are reused without creating the extractor.
